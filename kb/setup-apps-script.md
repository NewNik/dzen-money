# Установка в Google Apps Script

По умолчанию скрипт работает в режиме dry-run: читает письма, сверяет с Дзен-мани и пишет в журнал, но ничего не записывает. Запись включается свойством `MODE` (раздел 6).
Всё делается в **основном** аккаунте Google, кроме шага 2.

## 1. Фильтр в основном Gmail
Настройки → «Фильтры и заблокированные адреса» → «Создать фильтр»:
- От: `VCBDigibank@info.vietcombank.com.vn`
- Действие: «Применить ярлык» → новый ярлык `zen/inbox`.

## 2. Второй ящик: автопересылка
Во **втором** Gmail:
1. Настройки → «Пересылка и POP/IMAP» → «Добавить адрес пересылки» → основной адрес. На основной ящик придёт письмо с кодом — подтвердить.
2. Создать фильтр: От `VCBDigibank@info.vietcombank.com.vn` → «Переслать на» основной адрес.

Пересланное письмо сохраняет отправителя банка, поэтому в основном ящике на него сработает фильтр из шага 1. Скрипт и токен — одни на оба счёта.

## 3. Проект Apps Script
1. Открыть https://script.google.com → «Создать проект», назвать `dzen-money`.
2. В файл `Код.gs` вставить целиком содержимое `app/build/Code.js` (заменив всё, что там было).
3. «Настройки проекта» → включить «Показывать файл манифеста appsscript.json» → вставить в него содержимое `app/build/appsscript.json`.
4. Сохранить. На панели над кодом, в выпадающем списке функций (справа от кнопок «▷ Выполнить» и «Отладка»), выбрать `install` и нажать «▷ Выполнить». После выдачи доступа (шаг 5) внизу откроется «Журнал выполнения» со строкой «Метки созданы, таймер установлен (каждые 5 минут).»
   > Синюю кнопку «Начать развертывание» в правом верхнем углу **не нажимать**: она публикует скрипт как веб-приложение или API. Здесь это не нужно, таймер работает без развертывания.
5. Google попросит доступ к почте. Появится предупреждение «приложение не проверено» — это нормально для личного скрипта: «Дополнительные настройки» → «Перейти на страницу dzen-money».

`install` создаёт ярлыки `zen/*` и таймер на каждые 5 минут. Остановить — функция `uninstall`.

## 4. Проверка
- Дождаться нового письма банка (или вручную повесить ярлык `zen/inbox` на старое).
- Через 5–10 минут: слева «Выполнения» → запуск `run` → в журнале строка `[dry-run] parsed … 74000 VND …`.
- Письмо получает ярлык:

| Ярлык | Что значит |
|---|---|
| `zen/done` | записано в Дзен-мани (или уже было записано) |
| `zen/dryrun` | готово к записи, но режим dry-run |
| `zen/duplicate` | похоже на операцию, внесённую вручную (тот же счёт и сумма, дата ±1 день) — не записано, проверить |
| `zen/unparsed` | формат письма или счёт не распознан — причина в журнале |
| `zen/quarantine` | не прошла проверка отправителя или DKIM/DMARC |
| `zen/error` | исключение в скрипте, нет `ZEN_TOKEN` или 5 сбоев Дзен-мани подряд |

Запустить разбор сразу, не дожидаясь таймера: выбрать в списке функций `run` → «▷ Выполнить».

### Повторный разбор письма
Скрипт запоминает (свойство `PROCESSED_IDS`) только письма с окончательным итогом: `zen/done`, `zen/duplicate`, `zen/quarantine`. Остальные (`zen/dryrun`, `zen/unparsed`, `zen/error`) разбираются заново, если снять ярлык и повесить `zen/inbox`.
Запомненное письмо пропускается, в журнале `skip msg=… уже обработано`.

### Записать операцию заново (REDO)
Нужно, если операцию из письма удалили в Дзен-мани и хотят записать снова (например, после нового правила категории). Обычно скрипт удалённое не восстанавливает.
1. Свойство скрипта `REDO` = Order Number (несколько — через запятую). Номер — в журнале (`order=…`) или в комментарии операции `[vcb:…]`.
2. Повесить на письмо `zen/inbox`, запустить `run`. В журнале `restore id=…` (или `create`) и `записано`. Удалённое Дзен-мани по старому id не восстанавливает, поэтому у новой операции id другой (`vcb:<order>:r1`, `r2`, …).
3. После записи номер сам удаляется из `REDO`. В режиме dry-run — только строка в журнале, `REDO` не меняется.

Проверка на ручной дубль для номеров из `REDO` не делается. Если операция с этим id есть и не удалена, она не трогается (`exists`).

## 5. Образец для фикстуры
Выполнить функцию `dumpSample` — в «Черновиках» появится письмо `zen sample: …` с обезличенным HTML последнего письма банка (цифры → `0`, значения полей → `x`, ссылки убраны). Просмотреть, что не осталось имён и номеров, и передать текст для фикстуры.

## 6. Запись в Дзен-мани (этап 3)
Свойства скрипта («Настройки проекта» → «Свойства скрипта»):

| Свойство | Значение |
|---|---|
| `ACCOUNTS` | `{"<номер счёта VCB>":"<UUID счёта в Дзен-мани>", …}` — номера только цифрами; в git не класть |
| `ZEN_TOKEN` | токен Дзен-мани (zerro.app/token). Даёт полный доступ к учёту — только сюда, не в чат и не в git |
| `MODE` | не задано — dry-run; `write` — запись включена |

1. После обновления кода выполнить вручную `checkZen`. Google попросит новое разрешение — «Подключение к внешнему сервису» (запросы к api.zenmoney.ru). В журнале: «Токен работает», по каждому счёту из `ACCOUNTS` — «счёт найден», режим.
2. Неделю-две в dry-run: в журнале `run` для каждого письма строка `create id=… -245000 acc=… comment="…"` — что будет записано; или `exists` / `manual-duplicate`.
3. Включить запись: `MODE` = `write`. Письма с `zen/dryrun`, которые нужно записать, вернуть в `zen/inbox`.
4. Выключить запись — удалить `MODE` или поставить любое другое значение.

Проверки перед записью (на каждый запуск, где есть разобранные письма, скрипт читает операции из Дзен-мани целиком, ~2,5 МБ):
- операция с тем же id (UUIDv5 от Order Number) уже есть → `exists`, не отправляется, правки в приложении не затираются;
- она удалена в приложении → `deleted`, не воскрешается;
- есть операция без маркера `[vcb:…]` на том же счёте с той же суммой, дата ±1 день → `manual-duplicate`, ярлык `zen/duplicate`;
- иначе → `create`. После записи сервер должен вернуть операцию в ответе, иначе `zen/error`.

Сбой Дзен-мани (сеть, 5xx, 401) — письмо остаётся в `zen/inbox` и повторяется в следующем запуске; после 5 сбоев подряд — `zen/error`. Счётчик в свойстве `RETRIES`.

### Дубли с ручным вводом
Перед записью скрипт ищет операцию, внесённую вручную: дата ±1 день, без маркера `[vcb:…]`.
- Та же сумма на том же счёте — дубль. Расход сверяется по всем своим счетам из `ACCOUNTS`: его могли записать на счёт второго владельца.
- Сумма записана по памяти — тоже дубль. Вариантов три:

| Вариант | Условие | Пример |
|---|---|---|
| Округление вверх | записанная сумма — ближайшее сверху «ровное» число: у настоящей суммы есть разряд, который округляется | 119 600 → 120 000, 267 000 → 270 000 |
| «Первые цифры такие» | первые цифры те же, хвост заменён нулями; только для некруглой суммы банка | 111 421 → 111 000 |
| Опечатка | та же длина числа, первые три цифры те же, отличается одна цифра или переставлены две соседние; только для некруглой суммы банка | 202 329 → 202 239 |

  Как проверяется округление вверх (единицы округления — 100, 500, 1 000, 5 000, 10 000 и так далее):
  - записанная сумма должна быть ровнее настоящей. 203 000 → 206 000 не дубль: 206 не ровнее, чем 203;
  - хвост меньше тысячи отбрасывается вверх всегда: 29 400 → 30 000;
  - тысячи и крупнее округляются, только если до ровного числа не дальше половины единицы и не больше 3 000: 267 → 270 да, 262 → 270 нет, 285 420 → 290 000 нет;
  - от суммы должны остаться хотя бы две значащие цифры: 267 → 270 да, 67 → 70 нет. Мелкие суммы помнят точно, а соседние цены встречаются часто. Для округления до «пятёрок» порог строже: 114 → 115 да, 74 → 75 нет.

  В причине у ярлыка `zen/duplicate` указан вариант совпадения.

В обоих случаях операция не создаётся, письмо получает ярлык `zen/duplicate`. Если это не дубль — записать через `REDO`.

## 7. Категории (этап 4)
Категорию ставят правила: первое совпавшее по получателю или назначению платежа. Без совпадения категория не передаётся — тогда её может угадать сам Дзен-мани (так 245 000 стало «Рестораны»).

- Встроенные правила — `app/config/rules.json`: сети и службы по имени получателя (EVN, MobiFone, WinMart, аптеки, зоомагазины и т. д.) и правило про курьеров. Попадают в `Code.js` при сборке. Откуда они взяты и с какой точностью работают — [category-rules.md](category-rules.md).
- Личные — свойство скрипта `RULES`, проверяются раньше встроенных. Сюда — люди и места, которых не должно быть в git:

```json
[
  {"match": "nguyen van a", "field": "payee", "tag": "Рестораны"},
  {"match": "tien nha", "field": "details", "tag": "Аренда", "payee": "Аренда квартиры"}
]
```

| Поле | Что значит |
|---|---|
| `match` | подстрока или `/регулярка/`; регистр и вьетнамские диакритики не важны (`Nguyễn` = `nguyen`) |
| `field` | `payee` — получатель (у дохода — отправитель), `details` — назначение платежа, по умолчанию оба |
| `tag` | название категории как в приложении (подкатегория — своим названием, например `Коммуналка`) |
| `tag` = `null` | категорию не ставить: правило только останавливает поиск (магазин со смешанными покупками, маркетплейс, платёжный шлюз) |
| `payee` | необязательно: каким получателем записать операцию |
| `amountMin`, `amountMax` | необязательно: сумма не меньше / строго меньше |
| `multipleOf` | необязательно: сумма кратна числу |
| `person` | необязательно: только расход физлицу — в имени получателя нет слов вроде `HO KINH DOANH`, `CONG TY`, `SHOP`, `MART` |

Последнее встроенное правило — про курьеров: расход физлицу на 140–450 тыс., кратный 1 000, записывается как «Доставка еды» (17 из 20 таких писем в истории). Человека, которому это не подходит, достаточно один раз добавить в `RULES` — личные правила проверяются раньше.

Ошибки (нет категории, неверная регулярка, неверный JSON) — в журнале запуска; `checkZen` тоже проверяет правила.
Правила действуют только на новые операции: уже записанные скрипт не меняет, категорию у них править в приложении.

## 8. Telegram (этап 6)
1. В Telegram открыть @BotFather → `/newbot` → придумать имя → получить токен вида `123456:ABC…`.
2. Свойство скрипта `TG_TOKEN` = этот токен. Только в свойства, не в чат и не в git.
3. Открыть своего бота в Telegram, нажать «Start» (или написать любое сообщение).
4. Выполнить функцию `tgSetup` — она найдёт чат, сохранит `TG_CHAT_ID` и пришлёт «dzen-money подключён».
5. Выполнить `install` ещё раз — добавится таймер `dailySummary` (21:00 по Вьетнаму).

Что приходит:

| Когда | Что |
|---|---|
| после запуска `run`, если что-то записано | ✅ `10.11 −245 000 VND · Доставка еды · ****0851` |
| дубль ручного ввода, не разобрано, карантин, ошибка | ⚠️ с причиной и ссылкой на письмо в Gmail |
| 401 от Дзен-мани, нет `ZEN_TOKEN`, ошибка в `RULES` | ❗ не чаще раза в 6 часов на одну проблему (свойство `ALERTS`) |
| 21:00 | 📊 сводка: записано и сумма за день, проблемы, что висит под ярлыками, тишина от банка 3+ дня |

Без имён контрагентов и полных номеров счетов. `TG_NOTIFY` = `problems` — присылать только проблемы и сводку (по умолчанию — и записи).
Статистика по дням — свойство `STATS` (14 дней), день последнего письма банка — `LAST_BANK_DAY`.
Сводку можно получить сразу: выполнить `dailySummary`.

## Перенос в другой ящик
Нужен, если уведомления банка переведены на другой адрес. Скрипт привязан к аккаунту Google, в котором создан, и читает только его почту — проект создаётся заново в новом аккаунте.

1. **Старый аккаунт:** открыть проект, выполнить `uninstall` (таймеры снимаются). Проект пока не удалять — из него копируются свойства. Если не остановить, сводка в 21:00 будет приходить дважды, а через три дня старый скрипт начнёт предупреждать о тишине от банка.
2. **Новый аккаунт:** фильтр из раздела 1 (От банка → ярлык `zen/inbox`). При создании отметить «Применить фильтр к соответствующим цепочкам писем» — так ярлык получат письма, пришедшие до переноса. Старые письма, уже записанные прежним скриптом, не страшны: операция с тем же Order Number получит итог `exists`.
3. Проект по разделу 3: код, манифест, `install`, выдать доступ.
4. Свойства скрипта перенести из старого проекта вручную:

| Свойство | Переносить |
|---|---|
| `ZEN_TOKEN`, `ACCOUNTS`, `RULES`, `MODE` | да, как есть |
| `TG_TOKEN`, `TG_CHAT_ID`, `TG_NOTIFY` | да, как есть — бот и чат те же, `tgSetup` не нужен |
| `PROCESSED_IDS`, `RETRIES`, `ALERTS`, `STATS`, `LAST_BANK_DAY`, `REDO` | нет — служебные, привязаны к старому ящику, создадутся сами |

   Надёжнее сначала не задавать `MODE` (dry-run), проверить первый запуск и только потом поставить `write`.
5. Выполнить `checkZen` (новое разрешение на внешние запросы) — «Токен работает», счета найдены. Затем `run` — письма с `zen/inbox` получают итоговые ярлыки.
6. Выполнить `install` ещё раз, если `TG_TOKEN` задан после первого `install` (нужен таймер сводки), и `dailySummary` — проверить, что сообщение пришло.
7. Автопересылка из второго ящика (раздел 2) теперь должна вести на новый адрес; в старом основном ящике фильтр и ярлыки `zen/*` можно оставить как архив.
8. Когда новый скрипт отработал день без ошибок — в старом проекте удалить свойства `ZEN_TOKEN` и `TG_TOKEN`.

## Обновление кода
Вставить новый `app/build/Code.js` поверх старого. Вариант для тех, у кого локально есть Node: `npx @google/clasp login`, положить `app/.clasp.json` с `scriptId` и `"rootDir": "build"`, затем `npm run push`.
